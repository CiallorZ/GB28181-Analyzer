## 二、原始字节：两级表达形式

### 2.1 信令层（SDP `y=` 字段）

从帧 #1 的 SIP body 中提取的原始字节：

```
偏移    字节（十六进制）
       79  3d  30  36  30  30  30  30  31  38  36  39
ASCII   y   =   0   6   0   0   0   0   1   8   6   9
```

逐字符 ASCII 码：

| 字符 | ASCII |
|---|---|
| `0` | 0x30 |
| `6` | 0x36 |
| `0` | 0x30 |
| `0` | 0x30 |
| `0` | 0x30 |
| `0` | 0x30 |
| `1` | 0x31 |
| `8` | 0x38 |
| `6` | 0x36 |
| `9` | 0x39 |

**要点：**
- 原文是**纯 ASCII 数字字符**，共 10 个字符
- **没有 `0x` 前缀**
- **没有任何进制标记**
- 前导 `0` 就是 ASCII `0x30`，是字符本身，不是填充位

### 2.2 媒体层（RTP 头 SSRC 字段）

从帧 #7464（流 `0x23C34D4D` 的首包）提取的原始字节：

```
TCP 载荷（RFC 4571）:
  04 0C                          <- 2 字节长度前缀 = 1036
  80 60 83 D9 00 12 AD 40        <- RTP 头前 8 字节
  23 C3 4D 4D                    <- SSRC 字段（4 字节）
```

RTP 头字段解析：

| 字段 | 原始字节 | 值 |
|---|---|---|
| V/P/X/CC | `80` | V=2, P=0, X=0, CC=0 |
| M/PT | `60` | M=0, PT=96 |
| Sequence | `83 D9` | 33753 |
| Timestamp | `00 12 AD 40` | 1224000 |
| **SSRC** | **`23 C3 4D 4D`** | **0x23C34D4D = 600001869** |

**要点：**
- SSRC 是 **4 字节二进制值**
- 按网络字节序（大端）解释：`0x23C34D4D`
- 十进制值：`600001869`
- 小端解释会得到 `0x4D4DC323`（错误，RTP 规定大端）

## 三、能否对得上：8/8 完全一致

### 3.1 数值比对

```
SDP 原文:        y=0600001869
                 ↓ 按十进制读（唯一可能，见 3.2）
                 600001869
                 ↓
RTP 原始字节:    23 C3 4D 4D
                 ↓ 按大端读
                 0x23C34D4D = 600001869
                 ↓
                 相等 ✅
```

### 3.2 为什么只能按十进制读

这是关键的排除性证明：

| 解释方式 | 结果 | 是否可能 |
|---|---|---|
| 十进制 | 600001869 = `0x23C34D4D` | ✅ 与实际流一致 |
| 十六进制 | `0x0600001869` = 25,769,810,025 | ❌ **11 位数，超出 32 位上限**（最大 4,294,967,295） |

**RTP 的 SSRC 字段在协议上是固定的 4 字节，最大只能表示 32 位无符号整数。**
按十六进制读会得到 33 位的数，物理上不可能出现在 SSRC 字段里。

**所以 `y=` 必然是十进制——这不是解释选择，是协议约束决定的。**

## 四、是否按协议自动协商：是，8/8 自动回显

这是最关键的发现，直接回答了「是否人工转换」的疑问。

### 4.1 SDP 协商的双向过程

GB/T 28181 的点播采用 SDP Offer/Answer 模型：

```
上级（Offer）                      下级（Answer）
    |                                  |
    |--- INVITE (SDP offer) ---------->|
    |      y=0600001869                |
    |                                  |
    |<-- 200 OK (SDP answer) ----------|
    |      y=0600001869  ← 原样回显    |
    |                                  |
    |--- ACK ------------------------->|
    |                                  |
    |<===== RTP 流，SSRC=0x23C34D4D ===|
```

### 4.2 抓包中的实际证据

**Offer（帧 #1，上级 → 下级）**

```
m=video 8808 TCP/RTP/AVP 96
a=recvonly
a=setup:passive
y=0600001869
```

**Answer（帧 #3，下级 → 上级）**

```
m=video 9 TCP/RTP/AVP 96
c=IN IP4 19.130.177.114
a=sendonly
a=setup:active
a=xstreamtype:28181tcp_rfc4571
y=0600001869        ← 与 offer 逐字节相同
```

**注意 answer 里的其他字段都变了：**
- 端口：`8808` → `9`（占位，实际由 TCP 连接决定）
- 地址：上级地址 → 下级地址
- `recvonly` → `sendonly`
- `setup:passive` → `setup:active`

**唯独 `y=` 保持了完全相同的值。**

这说明：**下级读懂了 `y=`，并主动回显确认会使用这个值。**

### 4.3 严格按 Call-ID 配对验证

按 `Call-ID` 匹配（不是按到达顺序，避免错配）：

| 设备 ID | Offer `y=` | Answer `y=` | 回显一致 |
|---|---|---|---|
| 44060453031329016499 | `0600001869` | `0600001869` | ✅ |
| 44060504201321020009 | `0600007488` | `0600007488` | ✅ |
| 44060504201321020005 | `0600001889` | `0600001889` | ✅ |
| 44060504201321020006 | `0600002594` | `0600002594` | ✅ |
| 44060504201321020007 | `0600009276` | `0600009276` | ✅ |
| 44060504201321020008 | `0600001755` | `0600001755` | ✅ |
| 44060504201321020010 | `0600007050` | `0600007050` | ✅ |

### 4.4 三段一致性闭环

## 五、回应「SSRC 格式取决于上下文」的说法

这个说法在**描述现象**上是对的，但在**归因**上需要澄清。

### 5.1 准确的说法

| 层次 | SSRC 的表达 | 原因 |
|---|---|---|
| SDP 信令层 | ASCII 十进制文本 | 为了**人类可读**，SDP 是文本协议 |
| RTP 媒体层 | 4 字节二进制 | 为了**传输效率**，RTP 是二进制协议 |

**这不是"两种格式"，而是同一个数值的两种载体。**

类比：身份证号写在纸上（文本）和存在数据库里（整数），
本质是同一个号，只是载体不同。

### 5.2 所谓「依赖双方实现、并非强制统一」

这个说法适用于**部分**实现差异场景，但**本抓包不属于此列**：

| 常见争议点 | 本抓包实际情况 |
|---|---|
| 对端是否回显 `y=` | ✅ 8/8 都回显了 |
| 回显值是否一致 | ✅ 8/8 完全一致 |
| 实际推流是否用协商值 | ✅ 8/8 都在用 |
| 是否需要人工进制转换 | ❌ 协议层已自动处理，解析器按规范读即可 |

**如果对端不回显 `y=`，或回显了不用，那才是实现问题。**
这个抓包里三项全对，所以「依赖实现、非强制」的免责说法不适用。

### 5.3 「优先以 SDP y= 返回值为准」这个建议本身是对的

但要注意：**这里的"返回值"指 Answer 中的 `y=`，不是 Offer 中的。**

本抓包中两者相同，所以无差别。
若将来遇到两者不同的情况（对端改写了 SSRC），
应以 **Answer 的 `y=`** 为准，因为那才是对端承诺实际使用的值。

**这正是我上一版工具的一个缺陷**：只读了 Offer 的 `y=`，没优先取 Answer 的。
已在 `session_builder.py` 中处理：

```python
s.sdp_ssrc = (answer.get('y_ssrc') or offer.get('y_ssrc') or '')
```

## 六、那么「上级看不到画面」到底是什么原因

**与 SSRC 无关。** 这条已完全排除，证据见上。

本抓包能证明的：

| 结论 | 证据强度 |
|---|---|
| SSRC 协商正确（offer/answer/实流三段一致） | ✅ 确证 |
| 媒体流完整到达上级（6340 包无丢无乱） | ✅ 确证 |

要确认这一点，需要上级平台的日志和 CPU 监控，抓包本身给不出答案。

## 七、验证方法（可自行复现）

对方可用 Wireshark 独立验证本文所有结论：

**1. 看 SDP 原文**

```
过滤器：frame.number == 1
展开：Session Initiation Protocol → Message Body
查看最后一行：y=0600001869
```

**2. 看 RTP SSRC 原始字节**

```
过滤器：tcp.srcport == 53867 && tcp.len > 10
展开：Data → 找到 RTP 头
SSRC 字段显示：0x23c34d4d
右键 → Copy → ...as Hex Dump，可见 23 c3 4d 4d
```

**3. 验证数值相等**

```
Wireshark 内置转换：
View → 或在显示过滤器输入
  0x0600001869 会被解析为 25769810025（33位，超出SSRC范围）
  600001869    转十六进制 = 0x23C34D4D  ✅
```

**4. 看 Answer 是否回显**

```
过滤器：sip.Status-Code == 200
展开 Message Body，找 y= 字段
与对应 INVITE 的 y= 对比（需按 Call-ID 配对）
```
