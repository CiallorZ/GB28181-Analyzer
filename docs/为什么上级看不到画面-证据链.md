## 一、先回答那个"矛盾"

你的疑问很关键：

> 转换十六进制后你说 SSRC 是匹配的，那为什么上级还是看不到画面？

**因为 SSRC 匹配 ≠ 能看到画面。**

这是两件完全不同的事：

| 环节 | 状态 | 证据 |
|---|---|---|
| SSRC 协商是否正确 | ✅ 正确 | 8/8 精确匹配 |
| 媒体流是否到达上级 | ✅ 到达 | 上级确实在收包 |
| 上级是否**能解码**这条流 | ⚠️ **未见证据** | 上级从不发 RTCP |
| 上级应用层是否跟得上 | ❌ **跟不上** | 窗口萎缩到 0 |

**SSRC 正确只说明"钥匙对上了"，不代表"门开了"。**

下级说"我发流了"是对的，流确实到了。
但流到了 ≠ 上级解出来了。

## 二、这个抓包抓在哪？

这是理解一切的前提。

### 角色识别

```
SIP 信令：
  19.130.171.5  (19.130.171.5)    <- 发 INVITE，是上级平台
  19.130.177.111  (19.130.177.111)  <- 收回 INVITE，是下级信令网关

媒体流：
  19.130.177.115   (19.130.177.115) ┐
  19.130.177.117   (19.130.177.117) ├-> 推流到 19.130.171.5:8808
  19.130.177.114   (19.130.177.114) ┘
```

### 关键：抓包点在**上级平台侧**

依据：

1. **上级发的 INVITE 时间 = 抓包起点 0.000s**（帧 #1）
   抓包一开始就正好是上级发 INVITE，说明抓包在上级机器/上级旁路

2. **媒体流向：下级 → 上级**（3 个下级 IP 全部推给 `hufxxxcq`）
   抓包能看到完整的推流过程

3. **上级的 TCP 窗口退化被完整记录**
   只有抓在上级侧才能看到上级接收窗口的变化

**所以这个抓包证明的是"上级收到了什么"，不是"下级发了什么"。**

## 三、上级到底收到了什么？

### 3.1 流确实到了，而且完整

以点位 `44060453031329016499`（渔村公园渔船停泊点）为例：

| 项 | 数值 |
|---|---|
| SDP 声明 SSRC | `y=0600001869` → `0x23C34D4D` |
| 实际流 SSRC | `0x23C34D4D` ✅ 一致 |
| 包数 | 6,340 |
| 时长 | 14.36 秒 |
| 分辨率 | 1280×720 |
| 数据完整性 | 无丢包、无乱序 |

**从抓包看，这条流完整无缺地到达了上级。**

### 3.2 但上级的接收窗口在萎缩

这是最重要的证据。看这条连接的 TCP 接收窗口：

```
14.437s   65160   <- 初始窗口，正常
16.242s   11962   <- 2 秒内掉到 18%
18.206s   18980   <- 之后一直在 18980 徘徊
20.285s   18980
22.325s   18980
24.602s   18980
26.854s   18980
```

**全程出现 37 次零窗口（window=0）。**

零窗口意味着：**TCP 缓冲区满了，应用层没来得及把数据读走。**
操作系统只能告诉对端"你先别发了"。

### 3.3 窗口萎缩说明什么

TCP 窗口是应用层读取速度的间接反映：

- 窗口正常维持 → 应用层读得快，跟得上
- 窗口持续萎缩 → 应用层读得慢，数据堆积
- 窗口归零 → 应用层完全卡住

**37 次零窗口 = 上级的应用层反复卡住。**

## 四、上级有没有在解码？

### 4.1 上级从不发 RTCP

正常行为：接收端收流后，应周期性发 RTCP RR（Receiver Report）反馈丢包率、抖动。

实际抓包：

```
上级 -> 下级的 TCP 载荷包数：0
```

**上级在 8808 端口上一个字节都没往回发。**

这有几种可能：
- RTCP 配置为不发送（部分实现如此）
- 上级根本没进到解码环节
- RTCP 走了另一条路径（RTCP-mux 未启用时可能用相邻端口）

**单从抓包无法断定是哪一种**，但可以确定：**没有接收质量反馈的证据。**

### 4.2 但数据确实在被 ACK

上级对每个数据包都回了 ACK（TCP 层正常），说明：
- 网络层通
- 数据到达了上级的操作系统
- 只是应用层消化得慢

**这是"网络没问题，应用层有问题"的典型特征。**

## 五、时间线上的关键疑点

```
 0.000s   INVITE #1（渔村公园渔船停泊点）
 1.008s   200 OK
 1.049s   ACK
          ↓ 等了 7.7 秒，什么都没有
 8.787s   INVITE #2
 8.943s   INVITE #3 #4 #5   <- 3 个同时
 8.962s   INVITE #6 #7 #8   <- 又 3 个同时
          ↓ 上级在 1 秒内连发 7 个点播
12.674s  首个 TCP 连接建立
13.555s  8 条主流陆续开始
          ↓ 14.5 秒时上级开始大量 FIN
14.538s  下级开始发 BYE（连续重传 7-8 次）
14.532s  上级 FIN 掉第一个短连接
          ↓ 但 8 条主流还在推
36.173s  抓包结束，7 条主流仍在传输
```

### 疑点 1：为什么 1 秒内并发 8 路点播？

`8.787s` 到 `8.962s` 之间（175 毫秒），上级连续发起了 7 个 INVITE。

单路 1280×720 约 3.5 Mbps，8 路合计约 **74 Mbps**。

如果上级是按照"目录列表逐个点播"实现的，这个并发量会瞬间打满带宽和 CPU。

### 疑点 2：为什么流没到就开始 BYE？

下级从 `14.538s` 就开始发 BYE，而媒体流持续到 `36.173s`。

在这 21 秒里，BYE 重传了 **156 次**（21 个 Call-ID 各 7-8 次）。

**下级认为会话已经该结束了，但流还在推。**

这可能是：
- 上级在 `14.5s` 时已经开始关闭这些会话（FIN 22 条短连接）
- 下级收到会话结束的信号，开始发 BYE
- 但推流线程没停下来（这是下级的问题）

### 疑点 3：抓包只有 36 秒

8 条主流中有 7 条在抓包结束时**仍在传输，没有 FIN**。

说明抓包是被**中途截断**的，不是自然结束。

如果上级在 36 秒之后仍在收流但看不到画面，需要**更长时间的抓包**才能判断。

## 六、所以问题到底在哪？

### 已排除

- ✅ **SSRC 不一致** —— 8/8 精确匹配
- ✅ **网络丢包/乱序** —— 0.04% 缺口，无乱序，抖动 7.74ms
- ✅ **TCP 连接方向** —— SDP 为 `a=setup:passive`（上级被动等连）+
  `a=recvonly`（上级只收），实际握手 `pbzicreb:53867 → 上级:8808`
  即下级主动建连推流，与语义一致

### 最可能是这两处之一

**① 上级应用层性能不足（证据最强）**

关键证据：
- 37 次零窗口
- 接收窗口从 65160 萎缩到 18980 并停滞
- 上级从不发 RTCP

8 路并发 74 Mbps，上级处理不过来，TCP 缓冲区堆积，
应用层读不走数据 → 解码器拿不到完整帧 → 画面卡住或黑屏。

**② 上级的解码器不支持某个具体参数**

需要看到上级的日志才能确认：
- 是不是 SPS/PPS 解析失败？
- 是不是 PS 封装格式不识别？
- 是不是分辨率超出能力？

## 八、还需要什么证据

这个抓包能证明"流到了、上级收得慢"，但不能证明"上级为什么解码失败"。

要定位到具体原因，需要：

| 需要的东西 | 谁能提供 | 能证明什么 |
|---|---|---|
| **上级平台的应用日志** | 上级 | 解码器报什么错 |
| **更长的抓包（>2分钟）** | 任一方 | 流是否持续、何时断 |
| **上级同时抓包** | 上级 | 自己发出去的和收到的是否一致 |
| **CPU/内存监控** | 上级 | 是否性能瓶颈 |
| **单路点播测试** | 上级 | 排除并发因素 |

**建议做一个对照实验**：

只点播 1 路（渔村公园渔船停泊点），看是否正常。
- 1 路正常、8 路异常 → 确认是并发性能问题
- 1 路也异常 → 是解码兼容性问题，与并发无关

**这个实验最快能区分两类原因。**


**"下级发流了"是真的，"上级收不到"也是真的。**
两者不矛盾——**流到了网络层，但卡在应用层。**

问题大概率不在 GB28181 协议实现，而在**上级平台处理 8 路并发时的性能**。
