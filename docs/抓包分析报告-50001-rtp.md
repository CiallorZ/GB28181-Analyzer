# 抓包分析报告

**分析对象**：`50001.pcap`（信令）+ `rtp.pcap`（码流）
**分析工具**：GB28181 Analyzer v1.0.0-P0
**分析时间**：2026-11-18
**分析依据**：GB/T 28181-2022

---

## 一、结论

**两个抓包点位于不同网络路径，拼不出完整的点播链路。真正的问题是：下级平台的 SIP 事务层不返回最终响应。**

具体三件事：

1. **`50001.pcap` 只有 UDP 信令，零 TCP 包** —— 但 SDP 协商的媒体走 TCP 8808。抓包点抓不到媒体，不是媒体没传。
2. **`rtp.pcap` 只有 TCP 媒体，零信令** —— 28 条流全在推，但没有任何 SIP 上下文，无法归属到具体会话。
3. **BYE 事务全部失败** —— 29 个 Call-ID 各重传 10 次，对端只回 `100 Trying`，从不给最终响应。这是确凿的对端缺陷。

**信号通了不等于媒体通了，媒体在推不等于画面能看。这两个包各自只能证明一半。**

## 三、50001.pcap 信令分析

### 3.1 总体

```
SIP 报文      706 条
业务会话      22 个
信令成功率    100.0%（22/22 收到 200 OK）
发现媒体      0 个
RTP 流        0 条
```

### 3.2 SIP 方法分布

| 方法 | 次数 | 说明 |
|---|---|---|
| BYE | **319** | 异常偏高，见 3.5 |
| INVITE | 22 | 与会话数一致 |
| ACK | 22 | 正常 |
| MESSAGE | 24 | 心跳/目录 |

### 3.3 响应码分布

| 响应码 | 次数 | 说明 |
|---|---|---|
| 100 Trying | **273** | 临时响应 |
| 200 OK | 46 | 22 个 INVITE + 24 个其他 |

**注意**：`100 Trying` 273 次 vs `200 OK` 46 次 —— 大量临时响应没有对应最终响应。

### 3.4 22 个会话的协商参数

| 参数 | 值 | 评价 |
|---|---|---|
| 传输方式 | **TCP 100%** | 与抓包内容矛盾（见 3.6） |
| 协商端口 | **8808 100%** | 统一 |
| SDP `y=` SSRC | **全部为空** | ⚠️ 不符合国标 |
| 涉及设备 | 8 个 | 440605042013210200xx 段 |
| 会话时长 | 32.09 – 59.16 s | 两批（55s / 32s） |

**SDP `y=` 全空是明确缺陷**：GB/T 28181 要求 `y=` 字段携带 SSRC，
用于把 RTP 流匹配回会话。22 个会话全部为空，说明下级平台 SDP 构造不规范。

### 3.5 BYE 事务失败（确凿缺陷）

抽一个典型 Call-ID 看完整过程：

```
  0.000s  BYE  →  cseq=1 BYE     ← 首次发送
  0.407s  BYE  →  cseq=1 BYE     ← T1 重传
  1.459s  BYE  →  cseq=1 BYE     ← 2×T1
  3.483s  BYE  →  cseq=1 BYE     ← 4×T1
  3.501s  100  ←  cseq=1 BYE     ← 对端只回 Trying
  7.584s  BYE  →  cseq=1 BYE
  7.584s  100  ←  cseq=1 BYE
 11.685s  BYE  →  cseq=1 BYE
 11.686s  100  ←  cseq=1 BYE
 15.787s  BYE  →  cseq=1 BYE
 15.787s  100  ←  cseq=1 BYE
 19.888s  BYE  →  cseq=1 BYE
 19.888s  100  ←  cseq=1 BYE
 23.990s  BYE  →  cseq=1 BYE
 23.990s  100  ←  cseq=1 BYE
 28.091s  BYE  →  cseq=1 BYE
 28.091s  100  ←  cseq=1 BYE
 32.192s  BYE  →  cseq=1 BYE     ← 直到超时
```

**统计**：
- 29 个 Call-ID，每个 BYE **重传 10 次**（共 319 次 = 29 × 11）
- 53 个 Dialog 中 **29 个有重传**
- 全部只收到 `100 Trying`，**从未收到 200 OK**

**性质**：重传节奏严格遵循 RFC 3261 的 T1 指数退避（0.5s 起，翻倍至 4s 封顶），
说明发送方 SIP 栈实现正确。**问题在接收方 —— 它处理了 BYE（回了 100），
但从未完成事务（不给 200）。**

这是明确的**对端 SIP 事务层缺陷**，不是网络问题。

### 3.6 为什么抓不到媒体（关键判断）

```
SDP 协商：  m=video 8808 TCP/RTP/AVP 96
实际抓包：  TCP 包数 = 0，UDP 包数 = 706
```

**结论：抓包点只抓了 SIP 信令的 UDP 流量，媒体走的 TCP 8808 完全没有经过这个抓包点。**

这意味着：
- ❌ 不能说「媒体没建立」—— 没有证据
- ❌ 不能说「端口不通」—— 没有证据
- ✅ 只能说「这个抓包点看不到媒体」

要判断媒体是否真通，必须**在媒体路径上补抓 TCP 8808**。

## 四、rtp.pcap 媒体分析

### 4.1 总体

```
TCP 报文      61,634
业务会话      0（无 SIP 信令）
RTP 流        28 条
总包数        74,337
合计码率      74.1 Mbps
时间跨度      0 – 36.97 s
平均抖动      7.74 ms
```

### 4.2 流特征

| 特征 | 值 |
|---|---|
| 传输方式 | TCP 100% |
| 目的端口 | **8808 100%**（与信令协商一致） |
| 源端口 | 27 个（随机高位端口） |
| 分辨率 | 1280×720 ×16 / 1280×724 ×8 / 1280×960 ×4 |

**28 条流全部成功解码出画面**，H.264 编码。

| SSRC | 包数 | 码率 | 抖动 | 缺口 | 分辨率 | 帧数 |
|---|---|---|---|---|---|---|
| 0x23c34d61 | 9,347 | 3,052 kbps | 6.44 ms | 0 | 1280×724 | 341 |
| 0x23c36340 | 9,281 | 3,012 kbps | 6.51 ms | 0 | 1280×720 | 184 |
| 0x23c34cdb | 9,280 | 3,049 kbps | 6.45 ms | 0 | 1280×720 | 127 |
| 0x23c35705 | 9,209 | 3,020 kbps | 6.51 ms | **29** | 1280×720 | 672 |
| 0x23c3618a | 9,189 | 3,025 kbps | 6.50 ms | 0 | 1280×720 | 307 |
| 0x23c35022 | 8,094 | 2,614 kbps | 7.34 ms | 0 | 1280×724 | 805 |
| 0x23c34d4d | 6,340 | 3,559 kbps | 4.26 ms | 0 | 1280×720 | 351 |
| 0x23c36a3c | 3,401 | 961 kbps | 15.54 ms | 0 | 1280×960 | 300 |

其余 20 条均为 500 包左右、约 2.8 Mbps、抖动 6.2–6.9 ms。

### 4.4 质量评价

**整体质量良好**：

- ✅ 28 条流中 **27 条序号缺口为 0**
- ✅ 抖动 6.2–7.7 ms（低于 50 ms 阈值，正常）
- ⚠️ 1 条流有 29 个缺口（0x23c35705 / 9,209 包，占 0.3%）
  - 但这是 **TCP 承载**，缺口更可能来自抓包缓冲区溢出，不能判定为网络丢包
- ⚠️ 4 条 1280×960 的流抖动偏高（15 ms），码率较低（961 kbps）

**结论：媒体侧本身没毛病。** 74 Mbps 总量、抖动个位数毫秒、几乎零丢包，
说明网络和编码器都在正常工作。

### 4.5 无法判断的部分

`rtp.pcap` **没有任何 SIP 信令**，所以：

- ❌ 无法把 28 条流归属到具体设备/会话
- ❌ 无法确认这些流是否由 `50001.pcap` 里的 22 个 INVITE 触发
- ❌ 无法判断是「上级收流」还是「下级推流」

**唯一的线索**：目的端口都是 8808，与 `50001.pcap` 的 SDP 协商端口一致。
但 SSRC 无法比对 —— 因为那边 `y=` 全是空的。

## 五、问题清单

按严重程度排序：

### P0 · 必须解决

**1. 下级平台 BYE 事务不返回最终响应**

- 证据：29 个 Call-ID 各重传 10 次，只收到 `100 Trying`
- 影响：会话无法正常释放，端口/资源长期占用；大量重传消耗带宽
- 定位：**对端 SIP 栈缺陷**（发送方重传节奏符合 RFC 3261）
- 建议：要求下级平台厂商检查 BYE 事务处理，确保返回 `200 OK`

**2. SDP `y=` 字段全空**

- 证据：22 个会话 100% 为空
- 影响：无法通过 SSRC 把 RTP 流匹配回会话，媒体归属不可判定
- 定位：下级平台 SDP 构造不规范，不符合 GB/T 28181
- 建议：要求厂商在 SDP 中填入 `a=y:<SSRC>`

### P1 · 需要补数据

**3. 抓包点覆盖不全**

- 证据：信令包 706 全 UDP，媒体包 61,634 全 TCP，两个点无交集
- 影响：无法拼出完整链路，无法判断媒体是否真通
- 建议：**在同一个网卡同时抓 SIP 和 TCP 8808**，或在媒体路径上补抓

**4. 媒体流无法归属**

- 证据：`rtp.pcap` 零信令
- 影响：28 条流不知道属于哪个设备、哪次点播
- 建议：同 3，需要信令+媒体同时抓到

### P2 · 观察项

**5. 1 条流有 29 个序号缺口**

- 证据：0x23c35705，9,209 包中缺 29 个
- 影响：轻微，TCP 承载下可能是抓包缓冲问题
- 建议：多抓几个点对比，暂不处理

**6. 4 条 1280×960 流抖动偏高**

- 证据：15 ms（其余 6-7 ms）
- 影响：轻微，仍在正常范围
- 建议：观察是否持续

## 六、建议的排查动作

按优先级：

| 序号 | 动作 | 验证方式 |
|---|---|---|
| 1 | 在**媒体网卡**上抓 TCP 8808 | 抓到 RTP 即证明原抓包点是盲区 |
| 2 | 检查 8808 端口是否有 TCP SYN/SYN-ACK | 有 SYN 说明设备在连；无 SYN 说明设备侧没发起 |
| 3 | 要求下级平台修复 BYE 响应 | 复测后 BYE 应只发 1 次并收到 200 OK |
| 4 | 要求下级平台补 SDP `y=` | 复测后 `y=` 应非空，可与 RTP SSRC 对上 |
| 5 | 信令+媒体同点抓包 | 能一次性还原完整点播链路 |

**最小闭环**：动作 1 + 3 就能定位 90% 的问题。

---

## 七、分析局限

这份报告必须说明的限制：

1. **单点抓包不能证明端到端状况** —— 两个包各自只覆盖链路的一半
2. **SIP 成功 ≠ 媒体成功 ≠ 画面可播放** —— 三层独立，本报告已分层陈述
3. **序号缺口 ≠ 网络丢包** —— 特别是 TCP 承载时
4. **无法判断客户端是否真的显示了画面** —— 需要客户端侧证据
5. **`rtp.pcap` 的 28 条流归属未知** —— 没有信令上下文
