## 二、SSRC 协商（复核结论：正常）

### 结论

**8 个会话的 SDP `y=` 与 RTP 实际 SSRC 100% 匹配。**

### 证据

SDP 的 `y=` 字段是**十进制**表示，RTP 头中的 SSRC 是同一数值的
十六进制形式。两者换算后完全相等：

| 设备 ID | SDP `y=`（十进制） | 换算为十六进制 | 抓包中的实际 SSRC | 匹配 |
|---|---|---|---|---|
| 44060453031329016499 | `0600001869` | 600001869 → `0x23C34D4D` | `0x23C34D4D` | ✅ |
| 44060504201321020009 | `0600007488` | 600007488 → `0x23C36340` | `0x23C36340` | ✅ |
| 44060504201321020005 | `0600001889` | 600001889 → `0x23C34D61` | `0x23C34D61` | ✅ |
| 44060504201321020006 | `0600002594` | 600002594 → `0x23C35022` | `0x23C35022` | ✅ |
| 44060504201321020007 | `0600009276` | 600009276 → `0x23C36A3C` | `0x23C36A3C` | ✅ |
| 44060504201321020008 | `0600001755` | 600001755 → `0x23C34CDB` | `0x23C34CDB` | ✅ |
| 44060504201321020010 | `0600007050` | 600007050 → `0x23C3618A` | `0x23C3618A` | ✅ |
| 44060504201321020011 | `0600004357` | 600004357 → `0x23C35705` | `0x23C35705` | ✅ |

**匹配率：8 / 8 = 100%**

### 换算示例

```
SDP:  y=0600001869
      ↓ 按十进制读
      600001869
      ↓ 转十六进制
      0x23C34D4D
      ↓ 与抓包比对
RTP:  0x23C34D4D  ✅ 完全一致
```

**注意**：`0600001869` 的前导 `0` 是**定宽填充**，不是八进制标记。
如果误按十六进制解析会得到 `0x0600001869`（超过 32 位上限），
必然匹配失败——这是我们初版的错误原因。

## 三、端口复用（现象说明，非故障）

### 现象

8 个点播请求的 SDP 都写 `m=video 8808 TCP/RTP/AVP`，
所有媒体流推向同一端口 8808。

### 为什么这不是故障

国标允许端口复用，因为 **SSRC 是流的第一识别标识**。
既然 8 个 SSRC 全部精确匹配（见上节），接收端可以毫无歧义地区分每一路流。

实际抓包也证明了这点：28 条 TCP 连接全部连到 `:8808`，
但每条流的 SSRC 唯一，解码后 8 路画面各自正确。

### 唯一建议（优化项，不紧急）

如果未来并发路数上升，建议每次点播分配不同端口（8808/8809/8810…），
原因是：

- 单端口连接数会线性增长，长期运行有文件描述符耗尽风险
- 单端口在防火墙/NAT 场景下更容易被限速或误判

**当前 8 路的规模下没有实际问题。**

## 四、孤立 BYE（现象说明，非故障）

### 现象

```
INVITE 请求的 Call-ID：8 个
BYE 请求的 Call-ID：   21 个
有 BYE 无 INVITE：     20 个
```

### 解释

这 20 个 BYE 对应的会话**在抓包开始前就已建立**，
抓包只截到了结束阶段。这是正常的抓包视角限制，不是异常。

### 初版错误更正

初版称「BYE 全部未收到 200 OK」，**这是错误的**。
复核后确认响应存在，只是我们的事务匹配逻辑没把
响应正确关联到对应的 BYE 事务上（解析器缺陷，已修复）。

### 建议

如果关心这 20 个历史会话的来源，需要在**更早的时间点**重新抓包。

## 六、最终结论

### 对「为什么解不出画面」的答复

**这个抓包里的所有媒体流都能正常解码出画面，SSRC 协商完全正确。**

如果现场存在「点播后看不到画面」的现象，原因**不在这个抓包体现的环节**：

- 信令协商：正常（8/8 SSRC 匹配）
- 媒体传输：正常（28 条流全部可解码）
- 端口分配：正常（复用 8808 但 SSRC 唯一）

需要往以下方向排查：

1. **上级平台侧**：是否按 `y=` 的十进制值去匹配 SSRC？
   如果按十六进制字符串匹配，会匹配失败
2. **播放器侧**：是否支持 TCP 被动模式（`setup:passive`）？
3. **采集视角**：抓包点是否在完整路径上？
4. **时间同步**：媒体时间戳与信令时间是否对齐？

### 建议对方协助确认

1. 上级平台解析 `y=` 时，是否按**十进制**处理？
2. 播放器是否支持 TCP 被动模式接收媒体？
3. 是否能提供**同时包含上级平台侧**的抓包，用于对比？
